# PART 1 — PRD (제품 요구사항 정의)

## 0. Executive Summary

부모님과 따로 살기 시작한 직후, 요리를 거의 해본 적 없는 완전 초보가 칼질·반죽 등으로 손을 위험하거나 지저분하게 쓰는 작업 중, 화면을 보지 않고도 음성으로 레시피를 한 단계씩 안내받으며 진행하는 음성 에이전트다. 핵심 가치는 시간 절약이 아니라 '완성도 손실 방지'다. TTS(Qwen3-TTS)와 STT(Whisper)를 모두 실제 도메인 데이터로 파인튜닝했고, 상시 마이크 기반 음성 파이프라인(STT → 의도분류 → 레시피 처리 → TTS)이 실제로 구동되어 실사용 중이다. 계정 로그인 없이 누구나 발화로 새 레시피를 등록할 수 있고, 등록된 레시피는 관리자 승인을 거쳐야 공개 조회에 노출된다.

**2026-08-27 팀 결정으로 범위에서 제거된 것 — 계정 로그인/회원가입/개인화 저장, 재료 대체(진행 중 재료 치환·취소).** 이 문서의 이전 버전(v0.8 최초 작성분)엔 두 기능이 Must로 명시돼 있었으나, 실사용 리포트 기반으로 팀이 명시적으로 걷어냈다(`docs/specs/remove_user_accounts.md`, `docs/specs/remove_ingredient_substitution.md`). 이 문서는 그 결정을 반영해 다시 쓴 것이며, 아래 어디에도 "구현 예정"으로 남겨두지 않는다 — 두 기능은 Out of Scope(4.4)로 명확히 옮겼다.

## 1. 배경 및 문제 정의

### 1.1 대상 사용자 페르소나 (ICP)

| 항목 | 내용 |
| --- | --- |
| 이름(가상) | 김민지 (24세, 사회초년생) |
| 상황 | 3개월 전 취업과 함께 처음으로 자취를 시작. 그전까지 부모님과 함께 살며 요리를 거의 해본 적 없음 |
| 요리 경험 | 라면, 계란후라이 정도만 가능. '큰술'이 숟가락으로 얼마인지도 감이 없음 |
| 기술 친숙도 | 스마트폰·앱 사용에는 익숙하나, 요리 앱/레시피 서비스는 처음 접함 |
| 동기 | 매번 배달음식만 시키는 게 부담스러워 직접 요리를 시도하고 싶으나 자신이 없음 |

### 1.2 하루 시나리오 (Day-in-the-Life)

퇴근 후 저녁, 민지는 처음으로 된장찌개를 만들어보기로 한다. 레시피 앱에서 재료와 순서를 확인하고 요리를 시작한다. 감자를 써는 도중 손에 물기와 전분기가 묻어, 다음 순서가 뭐였는지 확인하려 폰을 만지지 못한다. 손을 씻고 화면을 다시 보는 사이 이미 끓고 있던 육수 농도가 변했고, 이 상태에서 계속 진행하다 보니 결과물이 기대와 다르게 짜졌다.

### 1.3 Job To Be Done

요리 경험이 전무한 사람이, 처음 도전하는 요리에서 손이 바쁜 순간에도 화면을 다시 보지 않고 다음에 뭘 해야 할지 정확히 안내받아, 첫 시도부터 완성도를 잃지 않도록 돕는 것.

### 1.4 페인 포인트 상세

| # | 문제 | 메커니즘 | 현재 우회 행동 |
| --- | --- | --- | --- |
| 1 | 완성도 손실(핵심) | 손을 씻고 화면을 다시 보고 조리로 복귀하면, 반죽 농도·양념 타이밍 등 되돌릴 수 없는 손실이 발생 | 감으로 대충 이어가거나, 처음부터 다시 시작 |
| 2 | 안전 | 칼질 등 위험 작업 중 집중력이 안전으로 쏠려 이전 단계를 잊음 | 조심스럽게 천천히 진행, 시간 소요 증가 |
| 3 | 시간 손실(부수) | 매번 손 씻고 확인하는 데 시간 소요 | 요리 자체를 포기하고 배달 시킴 |

## 2. 경쟁/유사 서비스 분석

| 구분 | SKT 누구 / KT 기가지니 | ChefEar(본 프로젝트) |
| --- | --- | --- |
| 레시피 콘텐츠 | 전문 콘텐츠 업체(이밥차)와 계약해 확보한 완성된 조리 콘텐츠 | 공개 데이터(만개의레시피) 기반, 조리순서 포함 60,282개 고유 요리명 전량 확보 |
| 진행 방식 | 단계별 안내 + '다음/다시' 명령 지원(이미 검증된 패턴) | 동일 패턴 채택(검증된 UX 재사용) + 상시 마이크로 매 발화마다 버튼 없이 계속 듣는 방식 |
| 콘텐츠 신뢰성 | 전문 업체 계약 콘텐츠 — 사전 검증됨 | 표준 데이터는 조회수 기반 자동 채택(대표성 실측), 사용자 등록분은 관리자 승인(Y/N)을 거쳐야 노출 — 검수 없는 콘텐츠가 그대로 서비스에 섞이지 않음 |

차별점: 표준 데이터의 대표성(조회수 기반 자동선정, 6.1 실측)과, 사용자가 새로 등록하는 레시피에도 관리자 승인이라는 품질 관문을 두는 것이 본 프로젝트의 핵심 차별점이다. 단계별 안내 자체는 이미 검증된 패턴이므로 그대로 채택했다.

### 2.1 앱 기반 경쟁 서비스 비교

| 구분 | 레시피오 | 레시핏 | 만개의레시피(자체 앱) | ChefEar(본 프로젝트) |
| --- | --- | --- | --- | --- |
| 인터랙션 방식 | 텍스트 채팅(타이핑 후 화면으로 확인) | 음성 핸즈프리(유튜브→레시피 변환, 정해진 명령어 방식) | 음성은 레시피 작성(입력)용, 안내(출력)용 아님 | 자유발화 기반 음성 안내(출력), 상시 마이크 + 임베딩 의도분류로 정해진 명령어 없이 이해 |
| 데이터 출처/신뢰성 | 확인 안 됨 | 사용자가 붙여넣은 유튜브 영상을 AI가 그때그때 변환 | 사용자 등록 20만여 개(레시피별 검증 절차 불명) | 조회수 1위 기준 표준레시피 자동선정(60,282건, 23% 대표성 확인) + 사용자 신규 등록은 관리자 승인 후에만 공개 |
| 신규 등록 | 불가 | 확인 안 됨 | iOS 앱은 레시피 등록 자체가 불가(스크랩만 가능), 안드로이드 앱·PC 웹에서만 가능 | 로그인 없이 발화만으로 요리명→재료→순서 등록, 관리자 승인 전까지는 등록한 사람에게도 비공개 |
| 비즈니스 성격 | 커머스(쿠팡 연동)+광고 배너 | 확인 안 됨 | 커머스(만개스토어) | 판매·결제 Out-of-Scope, '완성도 손실 방지' 단일 가치에 집중 |

차별점 정리: 본 프로젝트의 차별점은 '음성 지원 여부' 자체가 아니라 **①임베딩 유사도 기반 자유발화 이해(정해진 명령어 불필요) ②검증된 표준 데이터(조회수 기반 대표성) ③계정 없이도 가능한 등록 + 관리자 승인으로 품질 관리**의 조합에 있다. 재료 대체와 계정 기반 개인화 저장은 실사용 리포트를 바탕으로 팀이 범위에서 제외했다(4.4 Out of Scope).

## 4. 기능 요구사항 (제품 관점)

### 4.1 Must (반드시 구현, 구현 완료)

- 시작 인사말: 자유발화 유도(숫자선택 메뉴 없음), 상시 마이크로 버튼 클릭 없이 계속 듣는 방식
- 조회: 요리명 발화 시 표준 레시피(조회수 1위) 자동 안내, 1단계씩 짧게 진행
- 진행 제어: "다음/다시/이전" 발화로 조리 단계 이동, 1단계에서 "이전"은 현재 단계 유지
- 신규 등록: 로그인 없이 누구나 발화/텍스트로 요리명→재료→순서를 입력하고 최종 확인 후 저장(7.3)
- 등록 승인 워크플로우: 신규 등록 레시피는 `approved='N'`으로 저장되어 관리자가 승인해야 일반 조회에 노출
- 관리자 페이지: 토큰(1차) + 랜덤 단어 음성 화자검증(2차, ECAPA-TDNN)으로만 접근, 승인 대기 레시피 열람·승인·삭제
- TTS·STT 도메인 파인튜닝 완료 및 전/후 정량 비교(WER, CER, 청취평가)

### 4.2 Should (구현 완료)

- 화면에 현재 단계·재료·최근 대화 텍스트 병행 표시(음성 정보 보완용)
- 숫자+단위(예: 1.5컵) 정확 인식 및 조리 문맥 기반 고위험 오인식 보정
- 음성 인식/의도분류 실패 시 화면의 [이전] [다시] [다음] 수동 버튼으로 진행 흐름 복구
- 세션 내 반복 조회·조리 진행에서 이미 조회/합성한 결과를 재사용해 불필요한 DB·모델 재호출 생략(체감 지연 감소)

### 4.3 Could (여유 시 진행)

- TTS 톤 다양화(감정 음성 데이터셋 활용)
- UI 시각적 완성도 향상

### 4.4 Won't (Out of Scope / Do-Not-Build)

| 항목 | 제외 사유 |
| --- | --- |
| 사진으로 레시피 등록 | OCR/이미지인식은 STT/TTS 딥러닝 과제 범위 밖 |
| 서비스 응답 경로에서 외부 LLM API(OpenAI·Anthropic·Gemini·Groq 등) 호출 | 지도 강사 가이드 요건. 팀 GPU에 직접 올려 구동하는 로컬 LLM(EXAONE)은 외부 API가 아니므로 이 배제 대상이 아님(PART 2 1.5 참조) |
| 표준 데이터(60,282건) 밖 요리 요청 시 조리순서 실시간 생성 | 재료조차 없으면 정직 안내 후 신규 등록으로 유도 |
| 재료 궁합에 대한 AI 자체 판단·조언 | 신뢰성 검증 불가, 사용자 판단에 맡기고 시스템은 데이터 기반 반영만 |
| TTS 발화 도중 끼어들기(바지인) | 단계별 짧은 응답으로 이미 문제 해결, 구현 난이도 대비 효과 낮음 |
| 실제 판매·결제 연동 | 본 과제 범위 밖 |
| 자체 타이머 기능 | 사용자의 다음/다시/이전 명령을 대기하는 구조로 범위를 제한 |
| 자동 손 씻기 감지 및 관련 로그 모니터링 | 센서·카메라 기반 감지 범위로 확장하지 않음 |
| 특정 구역/섹션으로 점프하는 "이전" 기능 | 현재 단계에서 한 단계 이전으로만 이동 |
| 조리 중 다른 요리로 전환 | 조리가 시작된 뒤 다른 요리를 조회하려면 반드시 처음 화면으로 돌아가야 함(오인식으로 진행 중이던 레시피가 갑자기 바뀌는 것을 막기 위함) — 조리 중엔 조회/등록 의도 자체를 무시 |
| **재료 대체(진행 중 재료 치환·취소)** | 2026-08-27 팀 결정으로 전면 제거(`docs/specs/remove_ingredient_substitution.md`). v0.8 최초 작성 시점엔 Must였으나, 실사용 리포트를 바탕으로 범위에서 뺐다 — 관련 코드(`substitution.py`)와 화면도 삭제됨 |
| **계정 로그인/회원가입, 개인화 저장(마이 레시피)** | 2026-08-27 팀 결정으로 전면 제거(`docs/specs/remove_user_accounts.md`). 등록 자체는 로그인 없이 가능하도록 남기고, 그 대신 관리자 승인 워크플로우로 품질을 관리하는 방향으로 대체함(4.1) — 관련 코드(`auth.py`/`identity.py`/로그인 화면·마이레시피 화면)도 삭제됨 |

## 5. 사용자 시나리오 (대화 예시)

**시나리오 A — 조회 및 진행**

사용자: "된장찌개 어떻게 만들어?"

AI: "된장찌개, 조회수 1위 표준 레시피예요. 이걸로 시작할까요?"

사용자: "응"

AI: "1단계, 멸치로 육수를 끓입니다." (이후 '다음' 발화마다 한 단계씩 진행)

**시나리오 B — 표준 데이터 밖 요리 요청 시 신규 등록(로그인 불필요)**

사용자: "문어초무침 어떻게 만들어?" (60,282건 표준 데이터에도 없는 요리명)

AI: "등록되지 않은 레시피예요. 새로 등록을 원하시면 '레시피 등록'이라고 말씀해 주세요."

사용자: "등록"

AI: (요리명 → 재료 → 순서를 차례로 물어본 뒤) "저장이 완료됐어요! 관리자 승인 후에 검색할 수 있어요."

**시나리오 C — 매칭 실패 시 정직한 안내**

사용자: "문어랑 성게로 만드는 요리 알려줘" (DB에 없는 요리명/조합)

AI: "등록되지 않은 레시피에요. 새로 등록을 원하시면 '레시피 등록'이라고 말씀해 주세요."

**시나리오 D — 관리자 승인**

관리자: (`/admin`에 토큰으로 접근 → 화면에 뜬 랜덤 한글 단어 3개를 소리 내어 읽어 화자검증 통과) → 승인 대기 목록에서 방금 등록된 "문어초무침"을 확인 → 승인

이후: 다른 사용자가 "문어초무침 어떻게 만들어?"라고 물으면 이제 정상 조회됨.

## 6. 완료 정의 및 검증 계획 (Given-When-Then)

**AC-14 핵심 시나리오 완주(주 기준)**
GIVEN 손에 재료가 묻은 상태를 가정한 시나리오(표준레시피 기준)
WHEN 화면 터치 없이 음성만으로 전체 조리 과정 진행
THEN 마지막 단계까지 중단 없이 완료

**AC-15 반복 질의 일관성(보조 기준)**
GIVEN 동일 레시피에 동일 질의 반복
WHEN 10~20회 반복 테스트
THEN 정확한 레시피/재료 반영

**AC-16 딥러닝 검증(TTS/STT)**
GIVEN TTS·STT 파인튜닝 전/후 동일 텍스트셋·음성셋
WHEN WER·CER·청취 평가 실시
THEN 파인튜닝 후 지표가 파인튜닝 전 대비 개선됨을 수치로 제시(발표자료 필수 포함)

## 7. 딥러닝 과제 정의 및 강사 가이드 준수

딥러닝 과제 범위는 TTS(Qwen3-TTS)와 STT(Whisper) 파인튜닝을 모두 포함한다. 지도 강사 가이드("1차 팀 프로젝트 가이드")에 따라, 배포된 서비스가 실행되는 동안 외부 LLM API(OpenAI·Anthropic·Gemini·Groq 등)를 호출하는 코드는 산출물에 포함하지 않는다. 개발 도구로서 LLM을 코드 작성·자료조사·문서화 등에 활용하는 것은 허용된다.

의도분류는 sentence-transformers 기반 임베딩 유사도 매칭으로 처리해 런타임 외부 LLM 의존을 제거했다. 여기에 더해, 자유발화에서 요리명을 추정하고 "등록하고 싶다"는 의도를 보조 판단하는 데에는 팀 GPU 데스크탑에 직접 올려 구동하는 로컬 LLM(LGAI-EXAONE/EXAONE-3.5-2.4B-Instruct)을 쓴다. 이 모델은 인터넷 너머 외부 서버로 텍스트를 보내는 API 호출이 아니라 팀이 소유한 GPU에서 완전히 로컬로 추론되므로, 강사 가이드가 금지하는 "외부 LLM API 호출"에 해당하지 않는다(PART 2 1.5 참조).

# PART 2 — SDD (시스템 설계서)

## 1. 개요 및 딥러닝 과제 범위

### 1.1 딥러닝 과제 범위 (명확한 경계)

| 구분 | 범위 | 비고 |
| --- | --- | --- |
| 파인튜닝 대상 | TTS(Qwen3-TTS-12Hz-1.7B) | KSS 데이터셋 기반 QLoRA 파인튜닝 후 merge, HF Hub(kimseunguk/qwen3-tts-kss-finetuned)에 업로드해 배포에서 로드 |
| 파인튜닝 대상 | STT(openai/whisper-large-v3-turbo) | QLoRA(4-bit NF4) 파인튜닝, 어댑터를 HF Hub(leeony/chefear-stt-large-v3-turbo)에 업로드. 배포는 CTranslate2 int8로 변환한 뒤 faster-whisper로 구동 |
| 임베딩 유사도(비파인튜닝) | 의도분류 — sentence-transformers(jhgan/ko-sroberta-multitask)로 발화를 벡터화, 기준 예문과 유사도 비교 | 서비스 실행 중 외부 LLM API 호출 없음 |
| 로컬 LLM(자체 호스팅) | 자유발화 속 요리명 추정 + 등록 의도 판단 보조 — LGAI-EXAONE/EXAONE-3.5-2.4B-Instruct | 팀 GPU에 `transformers.AutoModelForCausalLM`으로 직접 로드해 추론. 외부 API 호출이 아님(1.5 참조) |
| 실데이터 | KADX/만개의레시피 재료 목록, 요리명, 인분수, 조회수(60,282개 고유 요리명 전량) | 원문 그대로 사용 |
| 오프라인 생성(1회성, 배포 이전) | 조리순서(COOKING_STEPS) 본문 텍스트 | 만개의레시피 원본 데이터에 조리순서 컬럼이 없어, 나머지 필드(요리명·재료·인분수·조회수)는 실데이터 그대로 두고 조리순서 문장만 LLM(ChatGPT)로 사전 작성해 DB에 적재했다. 이 작업은 서비스 배포 전 1회성 오프라인 데이터 준비이며, 배포된 서비스는 이 결과를 저장된 값으로 조회만 하고 런타임에 문장을 생성하지 않는다(6.2 참조) |

### 1.2 정의 및 대상 사용자(ICP)

ICP: 부모님과 따로 살기 시작한 직후, 요리를 거의 해본 적 없는 완전 초보 — 레시피 자체를 처음 접해 재료명·계량·순서 감각이 전혀 없는 사람.
JTBD: 요리 경험이 전무한 사람이, 처음 도전하는 요리에서 손이 바쁜 순간에도 화면을 다시 보지 않고 다음에 뭘 해야 할지 정확히 안내받아, 첫 시도부터 완성도를 잃지 않도록.

### 1.3 서비스 실행 경로에서 외부 LLM API 호출 배제 원칙 (중요)

지도 강사 가이드에 따라, 배포된 서비스가 사용자 요청에 응답하는 경로에서 OpenAI·Anthropic·Gemini·Groq 등 외부 LLM API를 호출하는 코드는 산출물에 포함하지 않는다. 이 원칙은 "인터넷 건너 남의 서버로 텍스트를 보내 추론시키는 구조"를 막는 것이며, 팀이 소유한 GPU에 가중치를 직접 올려 완전히 로컬로 추론하는 것은 이 배제 대상이 아니다. 이에 따라 이 프로젝트는 두 갈래로 처리한다.

| 처리 | 방식 | 외부 API 여부 |
| --- | --- | --- |
| 의도분류(FR-01) | sentence-transformers 임베딩 유사도 매칭 | 아님(경량 벡터 연산) |
| 요리명 추정·등록 의도 보조 판단(FR-17) | 팀 GPU에 직접 로드한 로컬 LLM(EXAONE-3.5-2.4B) | 아님(완전 로컬 추론) |
| 조리순서 제공(FR-02) | 사전 적재된 실데이터 조회 | 해당 없음(생성 자체가 없음) |
| 관리자 화자검증(FR-22) | speechbrain ECAPA-TDNN, CPU 로컬 추론 | 아님(완전 로컬 추론, LLM도 아님) |

의도분류·요리명 추정·조리순서 제공·관리자 화자검증 어디에도 OpenAI·Anthropic·Gemini·Groq 등 외부 LLM API 호출은 없다.

## 2. 범위 정의

### 2.1 In-Scope

- 시작 인사말: 숫자선택 없이 자유발화 유도, 상시 마이크(WebRTC)로 세션 내내 계속 청취
- 조회: 동일 요리명 다건 시 조회수 1위를 표준으로 자동 채택(6.1 규칙, 되묻지 않음) → 진행 확인 → 1단계씩 짧게 안내 → "다음/다시/이전" 진행 제어
- "다음": 다음 단계로 이동 / "다시": 현재 단계 재안내 / "이전": 정확히 한 단계 이전으로 이동. 1단계에서 "이전" 요청 시 1단계 유지
- 조리 중에는 새 요리로 전환하지 않는다 — 다른 요리를 조회하려면 반드시 처음 화면으로 돌아가야 한다
- 신규 등록(로그인 불필요, 누구나 가능): 요리명 → 재료 → 순서를 발화로 입력, 최종 확인 후 저장
- 등록 승인 워크플로우: 신규 등록은 `approved='N'`으로 저장되어 관리자가 승인해야 일반 조회에 노출. api_standard(표준 데이터)는 처음부터 승인된 것으로 취급
- 관리자 페이지(`/admin`, 일반 사용자 화면과 완전히 분리): 토큰(1차) + 랜덤 한글 단어 음성 화자검증(2차, ECAPA-TDNN)으로만 접근. 승인 대기 레시피 열람·승인·삭제
- 화면에 현재 단계·재료·최근 대화를 텍스트로 병행 표시
- 음성 인식/의도분류 실패 시 화면의 [이전] [다시] [다음] 수동 버튼으로 진행 흐름 복구
- TTS·STT 도메인 파인튜닝(계량단위 발음·짧은 안내 억양 등)

### 2.2 Could (스트레치 골)

- TTS 톤 다양화(감정 음성 데이터셋 활용)
- UI 시각적 완성도 향상

### 2.3 Out-of-Scope (Do-Not-Build)

- 사진으로 레시피 등록
- 서비스 응답 경로에서 외부 LLM API 호출(로컬 자체 호스팅 LLM은 예외, 1.3 참조)
- 표준 데이터(60,282건) 밖 요리의 조리순서 실시간 생성
- LLM의 자체 판단형 조언(궁합 등)
- TTS 발화 도중 끼어들기(바지인)
- 실제 판매·결제 연동
- 자체 타이머 기능
- 자동 손 씻기 감지 및 관련 로그 모니터링
- 특정 구역/섹션으로 점프하는 "이전" 기능
- 조리 중 다른 요리로 전환
- **재료 대체(진행 중 재료 치환·취소)** — 2026-08-27 팀 결정으로 전면 제거(`docs/specs/remove_ingredient_substitution.md`)
- **계정 로그인/회원가입, 개인화 저장(마이 레시피)** — 2026-08-27 팀 결정으로 전면 제거(`docs/specs/remove_user_accounts.md`), 관리자 승인 워크플로우로 대체

## 3. 시스템 아키텍처

### 3.1 전체 처리 흐름

```
상시 마이크(WebRTC) 입력
  → VAD(silero-vad)로 발화 구간 자동 분리
  → STT(faster-whisper, CTranslate2 int8, 파인튜닝 어댑터 병합)
  → 단위 표기 정규화 + 조리 문맥 기반 고위험 숫자 보정 + 환각(hallucination) 방어
  → (조리 중이 아니면) 로컬 LLM(EXAONE)으로 요리명 추정 + 등록 의도 판단
  → 임베딩 의도분류(sentence-transformers)
  → 의도별 라우팅: 조회 / 진행·재청취·이전 / 등록
  → 응답 텍스트 확정
  → TTS(Qwen3-TTS, 파인튜닝) 합성 → 오디오 자동재생
  → 화면(현재 단계·재료·대화 기록) 갱신
```

조회 흐름: 자유발화 → STT → (로컬 LLM으로 요리명 추정) → 의도분류 → 동일요리명 다건 시 조회수1위 자동채택(단, `approved='Y'`인 행만 후보) → 진행 확인 → 1단계씩 안내(60,282건 전체 커버).

등록되지 않은 요리 흐름: 표준 데이터에 없거나 아직 승인되지 않은 요리명을 물으면 "등록되지 않은 레시피"/"심사 중"이라고 정직하게 안내하고(6.4), "레시피 등록"이라는 발화로 신규 등록 흐름으로 바로 넘어갈 수 있다.

완료 흐름: 마지막 단계 완료 → 완료 화면 안내 → (신규 등록의 경우) 저장 완료 + 관리자 승인 대기 안내.

### 3.2 신규 등록 흐름

로그인 불필요 — 누구나 바로 진입 가능: 요리명 질문 → 재료 질문(여러 턴 누적 가능) → 순서 질문(여러 턴 누적 가능) → 최종 확인 → 저장(`approved='N'`, 관리자 승인 대기). 등록한 사람 자신도 승인 전까지는 이 레시피를 조회할 수 없다.

### 3.2.1 관리자 승인 흐름

관리자 페이지(`/admin`)는 일반 사용자 화면과 완전히 분리된 별도 Streamlit 페이지이며, 존재 자체가 URL에 노출되지 않는다(토큰이 없으면 페이지 목록에도 등록되지 않음). 접근은 2단계:

1. **1차 — 접근 토큰**: `?admin_key=<ADMIN_ACCESS_TOKEN>`이 붙은 URL로만 접근(또는 메인 화면에서 "관리자 페이지 접근할게요" 류 발화로 이동만 트리거 — 실제 인증은 여전히 아래 2차가 막음)
2. **2차 — 음성 화자검증**: 화면에 뜨는 랜덤 한글 단어 3개를 소리 내어 읽고 녹음 → STT로 단어 일치(3개 중 2개 이상) 확인 + ECAPA-TDNN 화자 임베딩이 사전 등록된 관리자 목소리와 코사인 유사도 임계값(기본 0.55) 이상인지 확인. 5회 실패 시 해당 IP를 60초간 잠금(서버 메모리 기준, IP는 잠금 해제 즉시 삭제 — 개인정보 최소 보유)

인증 통과 후에는 승인 대기(`approved='N'`) 레시피 목록을 보고 각 건을 승인(`approved='Y'`로 변경) 또는 삭제할 수 있다. 관리자 목소리는 별도 등록 페이지(`/enroll?enroll_key=<ADMIN_ENROLL_TOKEN>`)에서 이름 + 발화 3회로 등록한다.

### 3.3 화면 구성

Streamlit 화면 컴포넌트로 구현되어 있으며, 화면 목록은 다음과 같다: `start`(시작) · `recipe_confirm`(레시피 확인) · `cooking_step`(단계 안내) · `cooking_complete`(완료) · `unclassified`(미분류 발화 안내) · `register_intro`(등록 전 확인 화면, 현재는 아래 참고) · `register_dish_name`(요리명 입력) · `register_ingredients`(재료 입력) · `register_steps`(순서 입력) · `complete`(등록 저장 완료). 별도 페이지: `관리자`(승인 대기 목록·승인·삭제), `관리자 등록`(목소리 등록, `/enroll`).

`register_intro`는 애초에 "표준 레시피에 없어 등록을 유도"하는 확인 화면으로 설계됐지만, "등록"이라고 직접 말하거나 로컬 LLM이 등록 의도를 확신하면 이 확인 화면을 건너뛰고 `register_dish_name`으로 바로 진입하도록 되어 있다(2026-08-22 결정 — 사용자가 이미 확정적으로 말한 의도를 다시 확인받을 필요가 없다는 판단). 그 결과 지금은 `register_dish_name`에서 "취소"를 말했을 때, 그리고 등록 세션 상태가 유실됐을 때의 방어적 fallback 경로로만 실제로 도달한다 — 화면 자체는 남아있지만 주된 등록 진입 경로는 아니다.

계정/로그인/마이 레시피 화면(`login`/`my_recipes`/`edit_recipe`)과 조회 실패 전용 화면(`no_match`)은 2026-08-27 제거됐다 — 로그인은 계정 시스템 자체가 없어졌고, 조회 실패는 화면 전환 없이 현재 화면에서 음성 안내로 대체됐다(화면 전환 잔상 문제가 반복돼 화면 자체를 줄이는 방향으로 결정).

화면 구성 요소: ① 요리명+진행단계 배지 ② 재료 칩 ③ 현재 단계 카드(큰 글씨 단계 텍스트) ④ 최근 대화 자막(마이크/스피커 아이콘) ⑤ 마이크 상태 표시줄 ⑥ [이전] [다시] [다음] 수동 제어 버튼(레시피 진행 중에만 노출). 수동 버튼은 음성 제어의 기본 경로를 대체하는 것이 아니라 음성 실패 또는 직접 화면 조작을 위한 대체 경로다.

### 3.4 상시 마이크 파이프라인

세션당 한 번만 마이크 연결(streamlit-webrtc)을 맺으면 화면이 전환돼도 같은 연결을 계속 사용한다. silero-vad 기반 세그먼터(`MicVadSegmenter`)가 "말하다가 조용해지면 거기까지 한 발화"로 프레임을 잘라 STT에 넘긴다. AI가 TTS로 응답하는 동안에는 자기 목소리를 다시 인식하지 않도록 재생 길이만큼 마이크 입력을 일시적으로 무시한다.

### 6.2 조리순서 데이터 구성

`recipes` 테이블에 요리명·재료·인분수·조회수 등 60,196건이 적재되어 있고, `recipe_steps` 테이블에 357,938건의 단계가 적재되어 있다(둘 다 `load_data.py`로 1회 적재). 요리명·재료·인분수·조회수 등 메타데이터는 원본 CSV의 실데이터 그대로다. 조리순서(`COOKING_STEPS`) 본문 문장은 만개의레시피 원본 데이터에 해당 항목이 없어, 배포 이전 단계에서 LLM(ChatGPT)이 재료 목록을 바탕으로 작성해 채워 넣었다 — 이 작업은 서비스가 실행되기 전에 끝난 1회성 오프라인 데이터 준비이며, `source=api_standard`로 함께 태깅된다. 배포된 서비스는 이렇게 준비된 `recipe_steps`를 조회만 할 뿐, 런타임에 조리순서 문장을 생성하지 않는다.

이 절은 재료 대체 기능(요리명/재료내용 2단계 검색, "취소해줘" 롤백)을 설명하던 자리였다. 2026-08-27 팀 결정으로 기능 자체가 전면 제거됐다(`docs/specs/remove_ingredient_substitution.md`, `orchestration/substitution.py` 삭제) — 절 번호는 결번으로 남기고 내용은 지운다.

### 6.4 조리순서 서비스 범위

60,282개 고유 요리명 전체에 대해 조리순서를 사전 적재해 두었으므로, 표준 레시피로 선정되는 모든 요리명(단, `approved='Y'`)에 대해 조리순서를 제공한다. 사용자가 60,282건 표준 데이터 밖의 요리명을 요청하거나, DB에는 있지만 아직 관리자 승인 전(`approved='N'`)인 요리명을 요청하면 각각 정직하게 "등록되지 않은 레시피예요"/"심사 중인 레시피예요"라고 구분해서 안내한다(전자는 신규 등록으로 유도, 후자는 승인을 기다리라고 안내). 로그인 여부와 무관하게 누구나 "레시피 등록"이라고 말하면 신규 등록 흐름으로 진입할 수 있다.

### 6.5 요리명 인식 보정

STT 결과가 실제 요리명과 정확히 일치하지 않아도 아래 3단계로 보정을 시도한다.

1. 완전일치 — 발화 전체가 요리명 그 자체인 경우
2. 부분일치 — 발화 안에 요리명이 그대로 들어있는 경우
3. 편집거리 유사도 — 한글을 자모 단위로 분해한 뒤 비교해, 된소리·거센소리나 애/에처럼 음소 하나 차이인 오인식(예: "된장치게"→"된장찌개")을 보정

추가로 두 가지 안전망을 둔다: 공백만 다르게 붙은 요리명("고등어 라테" vs "고등어라테")을 내용이 완전히 같으면 매칭하는 공백 무시 매칭, faster-whisper 디코딩 특성상 짧은 음절이 반복되는 경우("된장찌장찌개")를 접어서 재시도하는 반복 축약 매칭. 두 안전망 모두 "내용이 완전히 같은가"만 확인하므로 엉뚱한 다른 요리로 잘못 매칭될 위험이 없다.

### 6.6 의도분류 임베딩 유사도 매칭

sentence-transformers(jhgan/ko-sroberta-multitask)로 사용자 발화를 벡터화하고, 의도별 기준 예문 세트(`data/intent_examples/기준예문.csv`)와 코사인 유사도를 비교해 가장 가까운 의도를 선택한다.

| 의도 | 설명 |
| --- | --- |
| 조회 | 요리명을 말해 레시피를 찾는 의도 |
| 등록 | 새 레시피를 등록하고 싶다는 의도 |
| 진행 | 다음 단계로 이동 |
| 재청취 | 현재 단계를 다시 안내받고 싶음 |
| 이전 | 한 단계 이전으로 이동 |
| 감탄사 | "감사합니다"처럼 아무 명령도 아닌 발화 — 무시(음성/화면 응답 없음) |
| 미분류 | 어떤 의도와도 충분히 비슷하지 않음 — 화면 전환 없이 잡음으로 처리, 반복 응답하지 않음 |

재료대체·취소 의도는 2026-08-27 제거됐다(6.3 참고) — `data/intent_examples/기준예문.csv`에서도 해당 카테고리가 빠졌다.

판정은 threshold(1위 유사도가 이 값 미만이면 미분류)와 margin(1위와 2위 차이가 이 값 미만이면 임의로 고르지 않고 미분류)을 함께 사용한다. 조리가 이미 진행 중인 상태에서 "조회"나 "등록"으로 분류되는 발화는 무시하고 현재 레시피를 그대로 유지한다(FR-20) — 조리 중에는 오직 처음 화면으로 돌아가는 것만이 다른 요리로 전환하는 유일한 경로다.

### 6.7 Supabase 테이블

| 테이블 | 컬럼 | 설명 |

| recipes | id, dish_name, ingredients, source, origin_id, view_count, external_id, servings, owner_id, approved, created_at | 레시피 1건당 1행. source는 api_standard/user_custom만 허용. origin_id는 user_custom이 어떤 표준 레시피 기반인지 자기참조. **owner_id는 2026-08-27부로 항상 null**(계정/쿠키 개인화 제거로 "등록한 사용자" 추적을 그만둠 — 컬럼 자체는 나중에 다른 식별자로 재사용할 수 있게 스키마엔 남겨둠). **approved('Y'/'N', 2026-08-27 추가)**: 'Y'면 조회에 노출, 'N'이면 관리자 승인 전. api_standard는 적재 시점에 항상 'Y' |

벡터검색은 SQL 함수 없이 Python(supabase-py의 `.eq()`/`.ilike()`/`.range()` 등)에서 필터를 조립한다. Supabase 자격증명이 없는 로컬 개발 환경에서는 인메모리 mock 클라이언트로 자동 대체되어 코드 수정 없이 실제 DB 연동 여부가 전환된다.

**관리자 성문(voiceprint) 저장은 Supabase가 아니라 로컬 JSON 파일**(`data/admin_voiceprints.json`, `{이름: {embedding: [192 float], sample_count, updated_at}}`)이다 — 저장소 폴더가 팀 네트워크 공유 드라이브라 파일도 기기 간 자연히 공유되고, 관리자가 소수라 테이블을 새로 만들 필요가 없다는 판단.

### 7.1 진행 단계 상태 전이

현재 step_number=N일 때: 다음 → N+1 / 다시 → N 유지 / 이전 → max(1, N-1), 1단계에서는 유지하고 "이전 단계 없음" 안내. 마지막 단계에서 "다음"을 요청하면 완료 화면으로 이동한다.

### 7.2 (결번) 재료 대체 응답 형식 — 2026-08-27 제거

이 절은 `{"match_type": "exact_name"|"ingredient_content"|"none", ...}` 형식의 재료 대체 응답을 설명하던 자리였다. 기능 제거와 함께 내용을 지운다 — 절 번호는 결번으로 남긴다.

### 7.3 신규 등록 상태 기계

`register_recipe(session, step, value)`가 step 값에 따라 동작한다: `dish_name`(등록 시작) → `ingredients`(여러 턴 누적 가능, 재료 확인 요약 텍스트를 함께 반환 — 단, 현재 UI는 이 요약을 음성으로 읽어주지 않고 텍스트 폼 확인 버튼만 씀) → `instructions`(여러 턴 누적 가능, 최종 확인 요약 텍스트 반환, 마찬가지로 UI는 텍스트 폼으로만 확인) → `confirm`(save_recipe 호출, source=user_custom·approved='N'으로 저장) / `abort`(세션 폐기, 저장 안 함). 동일 요리명으로 이미 user_custom이 있어도 덮어쓰지 않고 새 recipe_id로 별도 저장한다.

### 8.2 배포 아키텍처

배포는 팀 GPU 데스크탑(RTX 5070, 12GB VRAM) 한 대에서 Streamlit 서비스와 STT·TTS·임베딩·로컬 LLM 모델을 모두 상시 구동하는 방식이다. STT(faster-whisper)·임베딩(sentence-transformers)·로컬 LLM(EXAONE)·TTS(Qwen3-TTS) 넷 다 같은 GPU를 공유하므로, 단일 락으로 넷의 동시 추론을 직렬화해 자원 경합을 막는다(5.표의 "동시성" 행 참고 — 모델별 락 분리는 실험 후 되돌림). 관리자 화자검증(ECAPA-TDNN)은 CPU에서 별도로 돈다(GPU VRAM 여유가 거의 없어서). 모델 가중치는 Hugging Face Hub에서 앱 시작 시 내려받아 캐시하고, 데이터는 전량 Supabase에 저장한다(관리자 성문 파일 하나만 예외, 6.7 참고).

외부 접속은 Cloudflare Tunnel로 공개 도메인(chefear.store)을 통해 이 GPU 데스크탑에 연결된다. 별도 랜딩페이지(chefear-landingpage.vercel.app)를 거쳐 접속 링크로 안내하며, `.env`에 접속 토큰(ACCESS_GATE_TOKEN)을 설정하면 그 토큰이 붙은 URL로만 접근을 허용하는 약한 접근 제어를 둘 수 있다(비워두면 게이트가 꺼짐). WebRTC 마이크 연결은 Cloudflare Realtime TURN을 우선 사용하고, 설정돼 있지 않으면 자체 TURN(coturn) 또는 구글 공개 STUN으로 대체된다.
