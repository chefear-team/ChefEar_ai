# PART 1 — PRD (제품 요구사항 정의)

## 0. Executive Summary

부모님과 따로 살기 시작한 직후, 요리를 거의 해본 적 없는 완전 초보가 칼질·반죽 등으로 손을 위험하거나 지저분하게 쓰는 작업 중, 화면을 보지 않고도 음성으로 레시피를 한 단계씩 안내받으며 진행하는 음성 에이전트를 만든다. 핵심 가치는 시간 절약이 아니라 ’완성도 손실 방지’다. 딥러닝 과제로서 TTS(Qwen3-TTS)와 STT(Whisper) 모두 실제 도메인 데이터로 파인튜닝한다(v0.7 개정).

## 1. 배경 및 문제 정의

### 1.1 대상 사용자 페르소나 (ICP)

| 항목 | 내용 |
| --- | --- |
| 이름(가상) | 김민지 (24세, 사회초년생) |
| 상황 | 3개월 전 취업과 함께 처음으로 자취를 시작. 그전까지 부모님과 함께 살며 요리를 거의 해본 적 없음 |
| 요리 경험 | 라면, 계란후라이 정도만 가능. ’큰술’이 숟가락으로 얼마인지도 감이 없음 |
| 기술 친숙도 | 스마트폰·앱 사용에는 익숙하나, 요리 앱/레시피 서비스는 처음 접함 |
| 동기 | 매번 배달음식만 시키는 게 부담스러워 직접 요리를 시도하고 싶으나 자신이 없음 |

### 1.2 하루 시나리오 (Day-in-the-Life)

퇴근 후 저녁, 민지는 처음으로 된장찌개를 만들어보기로 한다. 레시피 앱에서 재료와 순서를 확인하고 요리를 시작한다. 감자를 써는 도중 손에 물기와 전분기가 묻어, 다음 순서가 뭐였는지 확인하려 폰을 만지지 못한다. 손을 씻고 화면을 다시 보는 사이 이미 끓고 있던 육수 농도가 변했고, 이 상태에서 계속 진행하다 보니 결과물이 기대와 다르게 짜졌다. 민지는 ’이럴 거면 그냥 배달 시킬걸’이라고 생각하며 다음 요리 시도에 대한 자신감을 잃는다.

### 1.3 Job To Be Done

요리 경험이 전무한 사람이, 처음 도전하는 요리에서 손이 바쁜 순간에도 화면을 다시 보지 않고 다음에 뭘 해야 할지 정확히 안내받아, 첫 시도부터 완성도를 잃지 않도록 돕는 것.

### 1.4 페인 포인트 상세

| # | 문제 | 메커니즘 | 현재 우회 행동 |
| --- | --- | --- | --- |
| 1 | 완성도 손실(핵심) | 손을 씻고 화면을 다시 보고 조리로 복귀하면, 반죽 농도·양념 타이밍 등 되돌릴 수 없는 손실이 발생 | 감으로 대충 이어가거나, 처음부터 다시 시작 |
| 2 | 안전 | 칼질 등 위험 작업 중 집중력이 안전으로 쏠려 이전 단계를 잊음 | 조심스럽게 천천히 진행, 시간 소요 증가 |
| 3 | 시간 손실(부수) | 매번 손 씻고 확인하는 데 5분 중 약 1분 소요(추정) | 요리 자체를 포기하고 배달 시킴 |

주의: 위 페인 증거는 실측이 아닌 요리 메커니즘 기반 추정이다. 개발 과정에서 완료정의(6장)의 반복 테스트로 실측 보완 예정이며, 발표 시에도 이 점을 투명하게 공유한다.

## 2. 경쟁/유사 서비스 분석

| 구분 | SKT 누구 / KT 기가지니 | ChefEar(본 프로젝트) |
| --- | --- | --- |
| 레시피 콘텐츠 | 전문 업체(이밥차)와 계약해 확보한 완성된 조리 콘텐츠 | 공개 데이터(만개의레시피) 기반, 조리순서 포함 60,282개 고유 요리명 전량 실데이터로 확보 |
| 진행 방식 | 단계별 안내 + ‘다음/다시’ 명령 지원(이미 검증된 패턴) | 동일 패턴 채택(검증된 UX 재사용) |
| 개인화 | 없음 — 정해진 레시피만 읽어줌 | 있음 — 사용자가 직접 등록/수정한 레시피를 저장·재현(user_custom) |
| 재료 대체 | 지원 안 함 | 진행 중 실시간으로 대체 재료 반영, 실제 유사 레시피 데이터 기반 추천 |

차별점 결론: 기존 서비스가 갖추지 못한 ’개인화 레시피 저장’과 ’진행 중 실시간 재료 대체’가 본 프로젝트의 핵심 차별점이다. 단계별 안내 자체는  이미 검증된 패턴이므로 새로 발명하지 않고 그대로 채택한다(제품 엔지니어링 원칙: 유사 제품 우선 검토).

### 2.1 추가 비교 — 앱 기반 경쟁 서비스(팀원 직접 사용 검증, v0.8)

강사 피드백에 따라 AI 스피커 플랫폼(누구/기가지니)뿐 아니라 실제 레시피 앱 3종을 팀원별로 직접 설치해 사용하고, 앱스토어 공식 정보로 교차 검증했다.

| 구분 | 레시피오 | 레시핏 | 만개의레시피(자체 앱) | ChefEar(본 프로젝트) |
| --- | --- | --- | --- | --- |
| 인터랙션 방식 | 텍스트 채팅(타이핑 후 화면으로 확인) | 음성 핸즈프리(유튜브→레시피 변환, 정해진 명령어 방식) | 음성은 레시피 작성(입력)용, 안내(출력)용 아님 | 자유발화 기반 음성 안내(출력), 임베딩 의도분류로 정해진 명령어 없이 이해 |
| 데이터 출처/신뢰성 | 확인 안 됨 | 사용자가 붙여넣은 유튜브 영상을 AI가 그때그때 변환(품질·일관성 미검증) | 사용자 등록 20만여 개(레시피별 검증 절차 불명) | 조회수 1위 기준 표준레시피 자동선정(60,282건, 23% 대표성 실측 확인) |
| 재료 대체 | 매칭 실패 시 즉시 거절, 대안 검색 없음 | 재생 컨트롤(다음 단계·타이머) 중심, 진행 중 재료 변경 대응 기능 미확인 | 없음 | ①요리명→②재료내용 2단계 검색 후에만 정직하게 안내, LLM 생성 없음(FR-04) |
| 개인화 저장 | 단순 북마크만, 수정본 별도 저장 불가 | 확인 안 됨 | **iOS 앱은 레시피 등록 자체가 불가**(스크랩만 가능), 안드로이드 앱·PC 웹에서만 등록 가능 | user_custom으로 수정본 별도 저장·재현, 플랫폼 무관(FR-08) |
| 비즈니스 성격 | 커머스(쿠팡 연동)+광고 배너 | 확인 안 됨 | 커머스(만개스토어) | 판매·결제 Out-of-Scope, ’완성도 손실 방지’ 단일 가치에 집중 |

⚠️ **레시핏 항목은 앱스토어 공식 정보 기준이며, 팀 내 실사용 테스트 결과(음성 지원 없음·식단관리 기능 위주로 보고됨)와 불일치가 확인되어 재검증 중이다(OI-12).** 테스트 대상이 동명의 다른 앱이었을 가능성이 있어 착수 전 재확인이 필요하다.

차별점 재정리(v0.8): 레시핏처럼 음성 기반 경쟁자가 이미 존재하므로, 본 프로젝트의 차별점은 ’음성 지원 여부’ 자체가 아니라 **①임베딩 유사도 기반 자유발화 이해(정해진 명령어 불필요) ②검증된 표준 데이터(조회수 기반 대표성) ③진행 중 실시간 재료 대체 ④플랫폼 무관 개인화 저장**의 조합에 있다.

## 3. 제품 목표 및 성공 기준

### 3.1 핵심 가치 우선순위

- ① 완성도 손실 방지(가장 강함, 되돌릴 수 없는 손실 방지)

## 4. 기능 요구사항 (제품 관점)

### 4.1 Must (반드시 구현)

- 시작 인사말: 자유발화 유도(숫자선택 메뉴 없음)
- 조회: 요리명 발화 시 표준 레시피(조회수 1위) 자동 안내, 1단계씩 짧게
진행
- 재료 대체: 요리명 매칭 → 재료내용 매칭 → 매칭 실패 시 정직한
안내(3단계, 시작 시점/진행 중 동일 적용)
- 신규 등록: 요리명→재료→재료확인→순서→최종확인의 2단계 확인 구조
- 완료 시 저장: 원본 보존 + 사용자 버전 별도 저장, 다음 조회 시 사용자
버전 우선 제공
- TTS·STT 도메인 파인튜닝 및 전/후 정량 비교(WER, 청취평가) — 둘 다 파인튜닝
대상(v0.7 개정)

### 4.2 Should (가능하면 포함)

- 화면에 현재 단계·재료·최근 대화 텍스트 병행 표시(음성 정보 보완용)
- 숫자+단위(예: 1.5컵) 정확 인식

### 4.3 Could (여유 시 진행)

- TTS 톤 다양화(감정 음성 데이터셋 활용)
- UI 시각적 완성도 향상(핵심 기능 완료 후)

### 4.4 Won’t (Out of Scope / Do-Not-Build)

| 항목 | 제외 사유 |
| --- | --- |
| 사진으로 레시피 등록 | OCR/이미지인식은 STT/TTS 딥러닝 과제 범위 밖 |
| 서비스 실행 중 외부 LLM API 호출 | 지도 강사 가이드 위반(1차 팀 프로젝트 가이드), 대신 임베딩 유사도·실데이터 검색으로 대체 |
| 표준 데이터(60,282건) 밖 요리 요청 시 조리순서 실시간 생성 | 위와 동일한 이유로 배제, 재료조차 없으면 정직 안내 후 신규 등록으로 유도 |
| 재료 궁합에 대한 AI 자체 판단·조언 | 신뢰성 검증 불가, 사용자 판단에 맡기고 시스템은 데이터 기반 반영만 |
| TTS 발화 도중 끼어들기(바지인) | 단계별 짧은 응답으로 이미 문제 해결, 구현 난이도 대비 효과 낮음 |
| 실제 판매·결제 연동 | 본 과제 범위 밖 |
| 자체 타이머 기능 | 현재 단계에서 사용자의 다음/다시/이전 명령을 대기하는 구조로 범위를 제한(SDD 2.3 동기화) |
| 자동 손 씻기 감지 및 관련 로그 모니터링 | 센서·카메라 기반 감지 범위로 확장하지 않음(SDD 2.3 동기화) |
| 특정 구역/섹션으로 점프하는 “이전” 기능 | 현재 단계에서 한 단계 이전으로만 이동(SDD 2.3 동기화) |
| 재료 대체 시 조리법 자체 재구성(예: 볶음→찜 전환), 양념 비율 재계산(신규, v0.5) | 이번 스프린트는 1:1 단순 재료 치환까지만 지원(FR-04 상세는 6.4). 2주 일정 내 스코프 이탈 방지가 목적이며, 이후 스프린트에서 재검토 가능 |
| 재료 대체 3개 이상 동시 처리(신규, v0.5) | 최대 2개까지만 동시 지원, 3개 이상은 순차 처리로 제한(완전 동시처리 보장 안 함) |

## 6. 완료 정의 및 검증 계획 (Given-When-Then, v0.6 개정)

지도 강사 SDD 교안 Ch5(완료기준) 기준으로 프로젝트 전체 완료 정의를 Given-When-Then 형식으로 재정리함. 기존 프로즈 서술은 아래 AC-14~16으로 대체.

**AC-14 핵심 시나리오 완주(주 기준)**
GIVEN 손에 재료가 묻은 상태를 가정한 시나리오(표준레시피 기준)
WHEN 화면 터치 없이 음성만으로 전체 조리 과정 진행
THEN 마지막 단계까지 중단 없이 완료 — 반복 테스트 성공률 목표치는 미정, 착수 후 실측해 확정

**AC-15 반복 질의 일관성(보조 기준)**
GIVEN 동일 레시피에 동일 질의 반복
WHEN 10~20회 반복 테스트
THEN 정확한 레시피/재료 반영 비율 — 목표치 미정, 1차 실측 후 확정

**AC-16 딥러닝 검증(TTS)**
GIVEN TTS 파인튜닝 전/후 동일 텍스트셋
WHEN WER·청취 평가 실시
THEN 파인튜닝 후 지표가 파인튜닝 전 대비 개선됨을 수치로 제시(발표자료 필수 포함), 구체적 개선폭 목표는 3.2 KPI와 동일하게 1차 실험 후 확정

## 10. 딥러닝 과제 정의 및 강사 가이드 준수

딥러닝 과제 범위는 TTS(Qwen3-TTS)와 STT(Whisper) 파인튜닝을 모두 포함한다(v0.7 개정). 강사 가이드에 STT는 API 연결만으로도 감점이 없다고 명시되어 있으나, 팀은 정량 지표(WER 전/후 비교)를 더 탄탄히 갖추기 위해 STT도 실제로 파인튜닝하기로 확정했다. 지도 강사 가이드(“1차 팀 프로젝트 가이드”)에 따라, 배포된 서비스가 실행되는 동안 외부 LLM API(OpenAI·Anthropic·Gemini·Groq 등)를 호출하는 코드는 산출물에 포함하지 않는다. 개발 도구로서 LLM을 코드 작성·자료조사·문서화 등에 활용하는 것은 허용된다. 조리순서 데이터는 초기에 LLM 오프라인 생성 방식을 검토했으나, 이후 동일 출처(만개의레시피)에서 실데이터(60,282건)를 별도 확보하면서 LLM 생성 방식은 전면 폐기했다(6.2 v0.4 개정). 의도분류는 sentence-transformers 기반 임베딩 유사도 매칭으로 대체하여 런타임 LLM 의존을 완전히 제거했다.

발표 시 원칙: 일반 시연(레시피 조회가 잘 되는 것)은 “시스템이 잘 작동한다”는 증거일 뿐 “딥러닝을 했다”는 증거가 아님. TTS·STT 모두 파인튜닝 전/후 Before·After 비교를 반드시 별도로 시연하여 구분 증명한다(v0.7 개정).

### 1.3 정의 및 대상 사용자(ICP)

ICP: 부모님과 따로 살기 시작한 직후, 요리를 거의 해본 적 없는 완전 초보 — 레시피 자체를 처음 접해 재료명·계량·순서 감각이 전혀 없는 사람.
JTBD: 요리 경험이 전무한 사람이, 처음 도전하는 요리에서 손이 바쁜 순간에도 화면을 다시 보지 않고 다음에 뭘 해야 할지 정확히 안내받아, 첫 시도부터 완성도를 잃지 않도록.
이 사용자가 칼질·반죽 등 손을 위험하거나 지저분하게 쓰는 작업 중, 화면을 보지 않고도 음성으로 레시피를 한 단계씩 안내받으며, 진행 중 재료를 바꾸면 즉시 반영되고, 완료 후 자신만의 버전으로 저장되는 음성 에이전트.

### 1.4 기획 근거 요약

핵심 가치 우선순위(소크라테스식 검증 결과): ① 완성도 손실 방지(손 씻고 복귀 시 반죽 농도·양념 타이밍 등 되돌릴 수 없는 손실 방지, 가장 강함) ② 안전(칼질 중 부주의 방지) ③ 시간 절감(부수 효과, 5분 중 약 1분 추정). 시작판정 3관문: 증거(중간, 실측 아님) / 중복(통과, 개인화+재료대체 즉시반영이 기존 서비스와 차별점) / 비용(통과, 무료 스택).

### 1.5 서비스 실행 중 외부 LLM API 호출 완전 배제 원칙 (중요)

지도 강사 가이드(“1차 팀 프로젝트 가이드”)에 따라, 배포된 서비스가 실행되는 동안 OpenAI·Anthropic·Gemini·Groq 등 외부 LLM API를 호출하는 코드는 산출물에 포함하지 않는다. 개발 도구로서 LLM을 코드 작성·자료 조사·문서화 등에 활용하는 것은 허용되나, 완성된 서비스가 사용자 요청에 응답하는 매 순간 LLM API를 호출하는 구조는 전면 배제한다. 이에 따라 의도분류(FR-01)는 임베딩 유사도 매칭으로, 재료 대체(FR-04)와 조리순서 제공(FR-02)은 실데이터 조회로만 한정하고, LLM 생성 fallback은 완전히 제거한다(조리순서는 6.2 v0.4 개정 참조).

## 2. 범위 정의

### 2.1 In-Scope

- 시작 인사말: 숫자선택 없이 자유발화 유도, 임베딩 유사도 매칭으로 의도 판단(조회/등록/진행·재청취/재료대체/취소) — "정정"은 별도 의도로 두지 않고 FR-07 제거와 함께 폐지(2026-08-25 개정, 아래 참고)
- 조회: 동일 요리명 다건 시 조회수 1위를 표준으로 자동 채택(6.1 규칙, 되묻지 않음) → 개요 설명 → 진행 확인 → 1단계씩 짧게 안내 → “다음/다시/이전” 등 진행 제어
- “다음”: 다음 단계로 이동 / “다시”: 현재 단계 재안내 / “이전”: 현재 단계에서 정확히 한 단계 이전으로 이동하여 해당 단계 재안내
- “이전”은 특정 구역·섹션·재료로 점프하지 않는다. 현재 1단계에서 “이전” 요청 시 1단계를 유지하고 이전 단계가 없음을 안내한다.
- 재료 대체(표준 제시 직후 “다른 버전으로” 요청과 진행 중 “~넣어도 돼?” 요청 모두 동일 로직 FR-04): ① 요리명 정확 매칭 변형레시피 검색 ② 없으면 재료 내용 기준 검색(6.4). ①②로 못 찾으면 정직하게 “해당 조합의 레시피가 없다”고 안내(LLM 생성 fallback 없음, 1.5 원칙)
- 조리순서: 초기 KADX 시드에는 원본 데이터가 없었으나(6.2 확인됨), 동일 출처(만개의레시피)에서 조리순서 포함 60,282건 실데이터를 별도 확보하여 고유 요리명 전량을 커버(6.2 v0.4 개정). 표준 데이터 밖 요리명 요청 시에만 정직하게 안내 후 신규 등록으로 유도(실시간 LLM 생성 없음, 1.5 원칙)
- 신규 등록: 요리명 → 재료 → 재료 확인 체크포인트 → 순서 → 최종 확인 체크포인트(2단계 확인)

- 완료 시 원본 보존 + 수정본 user_custom 별도 저장, 다음 조회 시 개인 버전 우선

- 음성 인식/의도분류 실패 시 화면의 [이전] [다시] [다음] 수동 버튼으로 진행 흐름을 복구할 수 있어야 함

### 2.2 Could (스트레치 골)

- TTS 톤 다양화(감정 음성 데이터셋 활용)
- STT 베이스 모델 비교 검증(Whisper vs 최신 후보)
- UI 시각적 완성도 향상(핵심 기능 완료 후 여유 시간에 진행, 3.4 참조)

### 2.3 Out-of-Scope (Do-Not-Build)

- 사진으로 레시피 등록 — OCR/이미지인식은 STT/TTS 과제 범위 밖
- 서비스 실행 중 외부 LLM API 호출(전면 배제, 1.5 원칙) — 의도분류·재료대체·조리순서 생성 어디에도 런타임 LLM 호출 없음
- 표준 데이터(60,282건) 밖 요리의 조리순서 실시간 생성 — 정직 안내 후 신규 등록으로 유도(6.5)
- LLM의 자체 판단형 조언(궁합 등) — “괜찮은지”는 사용자가 판단, 시스템은 데이터 기반 반영만 담당
- TTS 발화 도중 끼어들기(바지인) — 단계별 짧은 응답으로 이미 문제 해결됨, 구현 난이도가 팀 규모 대비 과함
- 실제 판매·결제 연동
- 자체 타이머 기능 — 현재 단계에서 사용자의 다음/다시/이전 명령을 대기하는 구조로 범위를 제한
- 자동 손 씻기 감지 및 관련 로그 모니터링 — 센서·카메라 기반 감지 범위로 확장하지 않음
- 특정 구역/섹션으로 점프하는 “이전” 기능 — 현재 단계에서 한 단계 이전으로만 이동

## 3. 시스템 아키텍처

### 3.1 조회 흐름

자유발화 인사 → STT(파인튜닝) → 의도분류(임베딩 유사도) → 동일요리명 다건 시 조회수1위 자동채택 → 개요설명+진행확인 → 1단계씩 안내(60,282건 전체 커버) 

재료 대체 요청 → ①요리명 정확매칭 검색 → 없음 → ②재료내용 기준 검색(6.4) → 없으면 정직하게 “없음” 안내(LLM 생성 없음)

완료 → user_custom 저장 확인

모든 응답은 TTS(파인튜닝)로 출력. 화면에 단계/재료/대화 텍스트 병행 표시(3.4). 서비스 실행 중 어디에도 LLM API 호출 없음(1.5)

### 3.3 화면 UI 구성 (Streamlit 최소 구현)

음성은 한 번 스쳐 지나가고 사라지므로, 화면이 “방금 뭐라고 했는지”를 붙잡아두는 역할을 한다. 목업 파일(recipe_ui_mockup.html) 기준 구성: ① 요리명+진행단계(N/5) 배지 ② 재료 칩(대체된 재료는 별도 색상+“(대체)” 표시) ③ 현재 단계 카드(진행률 점 표시+큰 글씨 단계 텍스트) ④ 최근 대화 자막(마이크/스피커 아이콘) ⑤ 마이크 상태 표시줄(듣는 중 표시+명령어 힌트) ⑥ [이전] [다시] [다음] 수동 제어 버튼.
Streamlit 기본 컴포넌트(st.chat_message, st.progress 등)로 최소 구현하고, 시각적 완성도는 핵심 기능(TTS 파인튜닝) 완료 후 여유 시간에 다듬는다(2.2 Could). 수동 버튼은 음성 제어의 기본 경로를 대체하는 것이 아니라 음성 실패 또는 직접 화면 조작을 위한 Fallback이며, 조리 중에도 쉽게 누를 수 있도록 충분한 터치 영역을 제공한다.

### 6.2 조리순서 데이터 확보 경위 및 최종 반영 (핵심 설계 결정, v0.4 개정)

모의테스트로 직접 검증한 사실: 초기 KADX 시드(4개 CSV, 234,538건) 18개 컬럼(재료 CKG_MTRL_CN, 소개글 CKG_IPDC, 조리방법분류 CKG_MTH_ACTO_NM 등) 어디에도 “1단계, 2단계…” 형태의 실제 조리 순서가 없음. 전체 234,538건 중 번호 패턴이 있는 185건(0.08%)도 실제로는 조리순서가 아닌 잡담(예: “야식으로 좋은 이유 4가지”)으로 확인됨. 원인 추정: 테이블명 자체가 “RECIPE_SEARCH”(검색용)이며, 만개의레시피가 검색 메타데이터만 무료 공개하고 실제 조리 콘텐츠는 자사 서비스로 트래픽을 유도하는 구조로 추정(대기업 ‘누구’·’기가지니’는 별도 계약 콘텐츠 업체(이밥차)를 사용하는 것으로 파악됨).

이에 개발 초기에는 재료 목록만 근거로 LLM(Claude)을 도구로 활용해 조리순서를 오프라인 생성하는 방식을 검토했으나(5,100건, 64.2% 부분 커버), 이후 동일 출처(만개의레시피)에서 조리순서(COOKING_STEPS)가 포함된 요리명별 데이터를 별도로 확보(60,282건, 무료·합법)하면서 **LLM 생성 방식은 전면 폐기**하고 이 실데이터로 전량 대체했다.

| 재료 목록(실데이터) | KADX CKG_MTRL_CN 원문 그대로 | source=api_standard |
| 조리순서(실데이터) | 요리명별_조리과정_60282건.csv, 요리명(CKG_NM) 다건 존재 시 조회수(INQ_CNT) 1위 기준 채택(6.1 표준선정규칙과 동일) | source=api_standard, 60,282개 고유 요리명 전량 커버. recipe_steps 테이블에 저장, 서비스는 조회만 함 |

### 6.4 재료 대체 검색 로직 (FR-04 상세, LLM 생성 fallback 제거)

실측 확인된 사례: “새우+바지락 둘 다”를 요청 시, 요리명 기준(“새우바지락된장찌개”) 검색은 0건이었으나, 재료 내용(CKG_MTRL_CN) 기준으로 검색하면 “해물된장찌개” 등 15건이 실제로 새우·바지락을 모두 포함하고 있음이 확인됨. 따라서 검색은 요리명 우선, 재료내용 차순으로 2단계만 수행하며, 둘 다 실패하면 정직하게 “없음”을 안내한다(LLM 생성으로 답을 만들어내지 않음, 1.5 원칙).

| 순서 | 검색 기준 | 신뢰도 |
| --- | --- | --- |
| ① | 요리명(CKG_NM) 정확 매칭 | api_standard급(실데이터) |
| ② | 요리명에 없으면 재료 목록(CKG_MTRL_CN) 내용 기준 검색 — 요청 재료가 모두 포함된 레시피 | api_standard급(실데이터, 이름만 다를 뿐 내용은 원문) |
| ③ | ①②모두 없으면 정직하게 “해당 조합의 레시피가 없습니다” 안내 | -(생성 없음) |

### 6.5 조리순서 서비스 범위 (전량 실데이터 확보로 확정, v0.4 개정)

60,282개 고유 요리명 전체에 대해 조리순서(COOKING_STEPS)를 실데이터로 확보했으므로(6.2), 표준 레시피(6.1 규칙)로 선정되는 모든 요리명에 대해 조리순서를 제공한다. 별도의 부분 커버리지 관리(배치 진행 추적 등)는 더 이상 필요하지 않다.

사용자가 60,282건 표준 데이터 밖의 요리명(신규 조합 등)을 요청하는 경우에는 재료대체 매칭 실패 시(6.4)와 동일하게 정직하게 “레시피가 없다”고 안내하고, 원하면 신규 등록 흐름(3.2)으로 직접 입력하도록 유도한다(실시간 LLM 생성은 하지 않음, 1.5 원칙 유지).

### 6.6 의도분류 임베딩 유사도 매칭 (FR-01, FR-15 상세)

sentence-transformers(ko-sroberta-multitask)로 사용자 발화를 벡터화하고, 의도별 기준 예문 세트와 코사인 유사도를 비교해 가장 가까운 의도를 선택한다. 기준 예문은 녹음용_문장스크립트_v1.csv의 카테고리를 재활용한다.

| 의도 | 기준 예문 출처 |
| --- | --- |
| 진행·재청취 | 진행재청취표현 카테고리(12개: “다음”, “다시 알려줘” 등) |
| 긍정·확정 | 긍정확정표현 카테고리(10개: “응”, “좋아” 등) |
| 조회·재료대체·등록 | 시나리오전체문장 카테고리(8개) + 요리명_조회문장(10개) |
| 취소(신규, v0.5) | “아니 그냥 원래대로”, “취소해줘”, “방금 건 취소” 등 신규 기준예문 세트 구축 필요(OI 추가) |

유사도 임계값(threshold)은 착수 후 실제 발화로 튜닝 필요(OI-09 참조).
판정은 threshold와 margin을 함께 사용한다. 최고 유사도가 threshold 미만이면 미분류로 처리한다. 최고 유사도가 threshold 이상이어도 1위와 2위 intent의 차이가 margin 미만이면 임의로 높은 intent를 선택하지 않고 미분류로 처리한다.

#### 7.1.1 진행 단계 상태 전이

현재 step_number=N일 때:
- 다음 → N+1
- 다시 → N 유지 후 현재 단계 재안내
- 이전 → max(1, N-1)
- 1단계에서 이전 → 1단계 유지 + 이전 단계 없음 안내
- 특정 구역·섹션으로 점프하지 않음
- 재료대체 후에는 변경된 recipe_id와 현재 step_number를 기준으로 동일 규칙 적용

### 7.2 classify_intent() 상세 명세

POST /internal/classify-intent (내부 함수 호출, 외부 API 아님)

요청:

```json
{
  "utterance": string,
  "context_recipe_id": string | null
}
```

응답 성공:

```json
{
  "intent": "조회" | "등록" | "진행" | "재청취" | "이전" | "재료대체" | "취소" | "미분류",
  "similarity_score": float,
  "matched_example": string
}
```

응답 실패(임계값 미달):

```json
{
  "intent": "미분류",
  "similarity_score": float,
  "fallback_message": "죄송해요, 잘 이해하지 못했어요. 다시 한번 말씀해주시겠어요?"
}
```

Edge Case (classify_intent)

| # | 상황 | 처리 방식 |
| --- | --- | --- |
| EC-01 | 모든 기준예문과의 유사도가 임계값(OI-09) 미만 | “미분류” 반환, 재질문 유도 문구 TTS로 출력 |
| EC-02 | 두 개 이상의 intent와 유사도가 근접(0.05 이내) | 가장 높은 것 채택하되, 로그에 근접 후보 기록(추후 기준예문 보강용) |
| EC-03 | “다시 진행해”처럼 재청취/긍정이 혼재된 모호한 발화 | 모의테스트로 확인된 사례 — 기준예문에 명시적으로 포함해 우선순위 부여(6.6) |
| EC-04 | 발화가 빈 문자열(STT 인식 실패) | classify_intent 호출 자체를 생략, “다시 말씀해주세요” 안내 |
| EC-05 | 맥락상 재료대체 발화지만 직전 레시피(context_recipe_id) 없음 | “어떤 레시피에 대해 말씀하시는 건가요?” 재질문 |

Acceptance Criteria (classify_intent)

AC-01 정상 분류
GIVEN 사용자가 “다음”이라고 발화
WHEN classify_intent() 호출
THEN intent=“진행” 반환, similarity_score ≥ 임계값

AC-02 모호 발화 재질문
GIVEN 사용자가 애매한 발화(“어… 그거…”)
WHEN 모든 기준예문과 유사도 임계값 미만
THEN intent=“미분류”, TTS로 재질문 문구 출력, 서비스 중단 없음

AC-07 이전 단계 이동
GIVEN 현재 step_number=3
WHEN 사용자가 “이전”이라고 발화
THEN step_number=2가 되고 2단계를 다시 안내

AC-08 1단계 이전 요청
GIVEN 현재 step_number=1
WHEN 사용자가 “이전”이라고 발화
THEN step_number=1 유지, 이전 단계가 없음을 안내

AC-09 수동 Fallback
GIVEN 음성 명령을 인식하지 못함
WHEN 사용자가 화면의 [다시] 버튼을 누름
THEN 현재 단계를 다시 안내

AC-10 intent 모호성
GIVEN 1위/2위 intent가 threshold를 넘지만 margin 미충족
WHEN classify_intent() 실행
THEN 임의 선택하지 않고 미분류 처리 후 재발화 요청

Acceptance Criteria (재료대체)

AC-03 요리명 매칭
GIVEN “바지락된장찌개” 진행 중, DB에 실존
WHEN “바지락 넣어도 돼?” 발화
THEN match_type=exact_name, 5초 이내 응답

AC-04 재료내용 매칭
GIVEN “새우+바지락” 요청, 이름 매칭 없음
WHEN 재료내용 검색 실행
THEN match_type=ingredient_content, “해물된장찌개” 등 반환

AC-05 매칭 완전 실패
GIVEN ①②모두 매칭 없음
WHEN search_by_ingredient_content()도 결과 없음
THEN match_type=none, 정직한 안내 메시지 반환(LLM 생성 없음)

AC-11(신규, v0.5) 재료 대체 취소
GIVEN 재료 대체가 이미 적용된 상태(session에 직전 recipe_id 기록됨)
WHEN 사용자가 “취소해줘”/“원래대로” 발화, 취소 의도로 분류됨
THEN cancel_substitution() 호출, 직전 recipe_id로 롤백, 5초 이내 응답
번호는 AC-06(이미 사용 중)과 충돌 방지를 위해 11부터 사용

### 7.5 register_recipe() / save_recipe() 상세 명세

POST /internal/register-recipe (다단계 세션형 호출)
1) 요리명 수집: `{ "step": "dish_name", "value": string }`
2) 재료 수집: `{ "step": "ingredients", "value": [string, ...] }` → 재료 확인 체크포인트(FR-06): 전체 재료 재낭독 후 확인 요청
3) 순서 수집: `{ "step": "instructions", "value": [string, ...] }` → 최종 확인 체크포인트: 재료+순서 전체 재낭독 후 확인 요청
4) 확정: POST /internal/save-recipe

```json
{
  "dish_name": string,
  "ingredients": [string, ...],
  "instructions": [string, ...],
  "source": "user_custom",
  "origin_id": null
}
```

응답: `{ "recipe_id": string, "saved": true }`

Edge Case (신규 등록)

| # | 상황 | 처리 방식 |
| --- | --- | --- |
| EC-14 | ~~재료 확인 체크포인트에서 사용자가 정정 요청(“문어 말고 낙지야”)~~ | **폐지(2026-08-25)** — FR-07과 함께 제거. 재료 목록이 틀렸으면 등록을 처음부터 다시 진행 |
| EC-15 | 순서를 한 번에 다 말하지 않고 여러 턴에 나눠 말함 | 세션 상태(step=“instructions”)를 유지하며 계속 append |
| EC-16 | 등록 중간에 사용자가 “그만할래” 발화 | 세션 폐기, 저장하지 않음, 초기 인사말로 복귀 |
| EC-17 | 동일 요리명으로 이미 user_custom이 존재 | 덮어쓰지 않고 새 recipe_id로 별도 저장(사용자가 여러 버전 가질 수 있음) |

Acceptance Criteria (신규 등록)

AC-06 2단계 확인 완료
GIVEN 요리명·재료·순서 모두 수집됨
WHEN 재료 확인 + 최종 확인 둘 다 사용자 긍정 응답
THEN save_recipe() 호출, source=user_custom으로 저장

## 8. 기술 스택 및 배포 아키텍처

### 8.1 버전 고정, 호환성 검증 및 학습 환경 분리

전제(v0.7 개정): TTS(Qwen3-TTS)와 STT(Whisper) 파인튜닝 장비 모두 GPU(CUDA)로 돌린다(노트북 RTX 4060 8GB / 데스크탑 RTX 5070 12GB). 두 모델 모두 HuggingFace transformers 계열 LoRA/전체 파인튜닝이 가능해, Piper 시절 필요했던 별도 학습 환경 분리 이유(torch 버전 충돌)가 더 이상 없다 — Piper는 11.2·8.3에서 배제됨에 따라 env-piper-train 분리를 제거하고 env-main 하나로 통합한다(간소화).

주의: TTS(Qwen3-TTS 1.7B) 전체 파인튜닝은 LoRA 대비 VRAM 요구량이 훨씬 크다 — 노트북(4060 8GB)에서는 사실상 어렵고, 데스크탑(5070 12GB)에서도 배치사이즈를 최소화해야 한다(실측 확인 중). 실제로 OOM 없이 완주 가능한지, 어느 epoch 체크포인트를 채택할지는 팀 자체 실측(loss curve, WER 추이)으로 확정한다.

호환성 검증(2026-08-08): sentence-transformers 5.6.1(요구 transformers≥4.41.0)이 env-main에서 문제 없이 동작 확인. Qwen3-TTS·Whisper 파인튜닝용 peft/bitsandbytes/accelerate 스택과의 전체 호환성은 착수 후 재검증 필요(OI, v0.7 신규).

주의: 아래 버전은 착수 전 잠정 고정값이며 임의로 변경하지 않는다. 실행 중 문제 발견 시 개별 판단으로 바꾸지 말고 반드시 팀장에게 보고 후 조정한다.

### 8.2 배포 아키텍처 (확정: Hugging Face Spaces)

이 장은 “배포된 서비스가 실제 사용자 질문에 답하는 추론 단계”에만 해당한다. 학습(파인튜닝) 단계는 여기 포함되지 않으며, 8.1장대로 모든 팀원의 학습 장비는 GPU(CUDA)로 돌리는 것을 전제로 한다.

검토 경위: Streamlit Community Cloud 무료 티어는 RAM 약 1GB로 이미 부족. 대안(로컬GPU+Cloudflare Tunnel, Modal, Colab+ngrok, Render) 비교 결과 Hugging Face Spaces(CPU Basic, 무료)가 배포 인프라로 잠정 선택됨.

⚠️ **미해결 리스크(v0.7 개정)**: 이 배포 계획은 원래 Piper(경량 onnx, CPU 친화적)를 전제로 확정한 것이다. TTS가 Qwen3-TTS(1.7B 파라미터 트랜스포머 LM)로 교체되면서, **GPU 없는 무료 CPU 환경에서 이 모델이 목표 응답시간(5초 이내) 안에 음성을 생성할 수 있는지 아직 실측하지 못했다.** 안 될 경우 옵션: ① GPU 지원 유료/제한적 무료 티어(Modal 등)로 전환 ② 데스크탑(5070)을 Tailscale로 상시 노출해 추론 서버로 활용 ③ Qwen3-TTS 0.6B 경량 모델로 축소. 착수 초반 실측 필수(OI, v0.7 신규).

| 항목 | 내용 |
| --- | --- |
| 스펙 | 2 vCPU, 16GB RAM, 완전 무료(카드 등록 불필요) |
| GPU 필요 여부(배포·추론 단계만) | 목표는 불필요이나 Qwen3-TTS 1.7B의 CPU 추론 속도 미검증(위 리스크 참조) |
| 배포 방식 | Streamlit 앱 + Whisper/Qwen3-TTS 모델을 HF Spaces 하나에 배포(Streamlit Cloud 별도 사용 안 함) |
| 모델 반입 방식 | git 저장소에 가중치 직접 커밋 금지 — Hugging Face Hub에서 앱 시작 시(@st.cache_resource) 다운로드 |
| 제약 | 48시간 비활동 시 슬립(재접속 시 30~90초 대기) → 발표 직전 warm-up 접속 필요(리스크 R-04와 동일 원리) |
| 데이터 저장 | HF Spaces 자체 저장공간은 재시작 시 초기화되므로 사용 안 함, 전량 Supabase에 저장 |
